# 부여 예약·탑승권 점검 (2026-11-02)

## 확인한 운영 설정과 확인하지 못한 사실

- 공개 홈페이지 `https://aquamobility.co.kr/api/regions`를 읽기 전용으로 조회했다. 통영·부여·합천이 `open`, 목포가 `closed`로 반환됐다.
- `/api/schedules/buyeo`와 `/api/schedules/buyeo/availability?date=2026-11-03`는 성공 응답을 반환했으며 부여 회차의 잔여석을 27석으로 표시했다. 이는 시스템 설정값이며 실제 차량 운행, 인증 완료, 가운행 실시를 입증하지 않는다.
- 가운행·군민 무료탑승 행사·정식운행의 확정 일정과 실시 여부는 확인되지 않았다. 이 변경은 운영 DB의 `open` 설정을 임의 변경하지 않는다. 실제 접수를 받기 전 운영 담당자가 상태·회차·판매 좌석을 확인해야 한다.
- 운영 서버에는 예약 생성·결제·취소·현장발권 요청을 보내지 않았다. 실고객 예약을 조회하거나 테스트 주문을 생성하지 않았다.

## 반영 내용

- 홈·지역 선택·부여 안내를 `/api/regions` 기반으로 통일한다. `open`만 예약 진입을 허용하고 준비·중단·미확인 상태는 접수를 차단한다. `hidden`은 노출하지 않는다.
- 근거가 확인되지 않은 4,531명·4.9점·지역 수를 실제 운행 지역 수로 표현한 부분을 제거한다. 부여 고정 예약 가능 문구와 하드코딩된 요금·시간표도 제거한다.
- 알림을 신청하지 않았는데 신청됐다고 표시하던 버튼은 실제 공지 화면으로 연결한다.
- 날짜별 잔여석 확인 전에는 좌석 선택을 허용하지 않는다. API 실패·누락·중단 회차는 예약 가능한 좌석으로 대체하지 않는다. 날짜 범위와 요일을 적용하고 날짜 선택 요청의 역순 응답을 무시한다.
- 체크아웃의 운영 상태를 확인하고 예약 제출 직전에 회차·잔여석을 재확인한다. 중복 제출을 막고 실패 안내를 표시한다.
- 예약 조회의 데모 데이터와 localStorage 대체 결과를 제거한다. 휴대폰번호 뒤 4자리 일치를 전체 일치로 변경한다.
- 결제 완료 화면은 저장된 장바구니로 QR을 새로 꾸미지 않고 서버의 탑승권 조회 화면을 사용한다. QR 데이터는 현장 입력 경로와 동일한 예약번호로 통일한다.
- QR은 서버 상태가 `confirmed`, `payment_done`, `checkedin`인 예약만 표시한다. 취소·환불·결제대기·노쇼·탑승완료·미확인 상태에는 사용할 QR을 표시하지 않는다.
- 모의 결제창의 테스트 완료 버튼으로 실예약 생성 요청을 보내던 연결을 제거한다. 이 저장소에는 실제 PG 승인 흐름이 구현돼 있지 않다. 정상 유료 예약 결제 기능을 완성한 변경은 아니다.
- QR 모달 뒤로가기는 조회 화면을 다시 렌더링하지 않고 닫는다. 독립 탑승권 화면은 예약확인 화면으로 돌아간다.
- 모든 모듈·스타일의 해시를 빌드 전에 HTML에 반영해 고객 모듈 변경도 캐시 버전에 반영한다.

## 검증

- `npm test`: 회귀시험 9개 통과. 운영 상태·API 실패·잔여석 누락 및 중단·운영 날짜 범위·인원 카운터·QR 상태 제한·최신 탑승권 재조회·데모/로컬 데이터 차단·전화번호 전체 일치·모의 결제의 확정 차단·좌석 재확인·실패 안내·중복 제출을 검사했다.
- `npm run build`: 빌드 및 기존 빌드 점검 통과.
- 수정한 고객 JS 파일의 `node --check` 및 `git diff --check` 통과.
- 브라우저 화면 검증은 실행하지 못했다. 환경에 Chromium이 없고 설치 다운로드가 유효한 압축파일을 반환하지 않았다. 실제 모바일 화면·카메라 스캔·프린터·SMS·PG 결제·실DB 저장 성공 여부를 검증했다고 볼 수 없다.

## 정식 접수 전 남은 작업

1. 실제 부여 운행 준비 상태와 가운행/무료행사/정식운행 일정을 확정하고 관리자 운영 상태·판매 날짜·회차·요금을 맞춘다. 현재 `open` 설정 자체가 실제 운행 개시를 뜻하지 않음을 유의한다.
2. 이 저장소는 `/api/*`를 별도 Express 서버(3001)로 전달한다. 백엔드 소스는 포함돼 있지 않다. 실제 PG 승인/웹훅 검증, 무료행사 대상자 검증, 서버측 예약 상태·금액 검증, 좌석 원자적 차감·멱등성은 백엔드에서 구현·확인해야 한다. 프론트 중복 제출 방지는 서버 중복 예약 방지를 대체하지 않는다.
3. 고객 예약 조회는 기존 공개 `/check/:예약번호`, `/ticket/:예약번호`를 유지했다. 휴대폰 비교는 클라이언트에서 수행된다. 백엔드에서 예약 접근 권한·전화번호 인증/서명된 조회 토큰·개인정보 최소 응답을 검증해야 한다. 전화번호 대체 조회도 기존 목록 API(최대 50개)에 의존하므로 누락 없는 안전한 전용 조회 API가 필요하다.
4. 별도 시험 환경에서 예약 신청 → 실제 승인 → DB 저장 → 문자 링크 → QR 조회 → 현장 스캔 → 취소·환불 후 QR 차단을 확인한다. 이번 변경은 운영 서버에 배포하지 않았다.

## 후속 지시 반영 — 운행 전 시스템 테스트 및 검색 노출

대표님이 실제 운행 전임을 확인했고, 예약을 막지 말고 전체 흐름을 테스트하도록 지시했다. 위 최초 점검 기록의 모의 결제 확정 차단 조치를 변경한다.

- `BookingState.testMode = true`로 테스트 안내를 표시하고 `open` 지역의 예약 진입을 유지한다. 부여를 `preparing`으로 변경하거나 강제로 접수 차단하지 않는다.
- 모의 결제 버튼을 테스트 예약 제출 → 서버 저장 응답 → 서버 QR 조회로 연결한다. 실제 PG 승인 요청이나 실제 카드 청구 기능은 구현하지 않았다.
- 예약자명에 `[테스트]`를 붙이고 `isTest`, `testMode`, `paymentMethod: test`를 함께 전송한다. 별도 백엔드가 이 필드를 수용·보관하고 매출 통계·알림에서 제외하는지는 아직 검증되지 않았다. 단순 표시만으로 DB 격리를 보장하지 않는다.
- 검색 대상: 수륙양용버스, 수륙양용시티투어, 부여수륙양용버스, 부산수륙양용버스, 통영수륙양용시티투어, 통영수륙양용버스 및 띄어 쓴 표현.
- 홈페이지 제목·설명·실제 HTML 본문·내부 링크를 수정하고 `/amphibious-bus`, `/buyeo-amphibious-bus`, `/tongyeong-amphibious-bus`, `/busan-amphibious-bus` 안내 페이지를 추가했다. 부산은 확정 운행·예약 상품으로 표시하지 않는다.
- 모든 검색로봇에 동일한 개인정보 경로 제외 규칙을 적용하고 사이트맵 URL 중복과 의미 없는 당일 수정일 표기를 제거했다. 예약 지역의 구조화 데이터에 미확인 주소·전화번호·영업시간·요금을 제공하지 않는다.
- 기존 검색엔진 소유확인 값을 보존했다. 네이버 서치어드바이저·Google Search Console 계정에서 소유확인·사이트맵 제출·색인 요청은 실행하지 않았다. 검색 순위나 즉시 노출을 보장하지 않는다.
